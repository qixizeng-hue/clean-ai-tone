# 公共文风画像（去 AI 化）

> 跨项目通用。机构专有锚点、验收口径写在项目层，不写本文件。

## 一句话

专业书面备忘体：有指标、有数值、有对比、有建议；可核对；无聊天腔、无教师姿态、无空泛打分。

## 场景分层

| 级别 | 场景 | 要求 |
|------|------|------|
| P0 | 对外/对客交付正文 | 书面语；首句尽量带指标与数值；禁止口语化 |
| P1 | 纪要、拍板说明 | 书面语，可略短 |
| P2 | 探索对话未落稿 | 可略松，仍禁套话与说教 |

## H1–H8（须清零）

1. 修辞性引号包裹概念、口号  
2. 破折号作舞台停顿（— – ──）  
3. 替读者发言（很多人觉得、你可能以为）  
4. 纠错说教（不是 X 而是 Y、真正的问题是）  
5. 教师式自问自答  
6. 贬低读者（小白一定要、你只需要）  
7. 空分析（这一步的关键是、核心在于）  
8. 空泛评价（效果非常好、变化很大）→ 改落到具体指标或句段  

## 公共硬规则

| 规则 | 要求 |
|------|------|
| 数值锚点 | 判断句尽量含指标名 + 数值；禁「整体表现良好」无数 |
| 强调 | 正文默认不加粗；确需强调时克制使用，禁止见数就加粗 |
| 符号 | 正文禁用修辞引号、破折号停顿、箭头 →、标题式【标签】 |
| 结构标签 | 用「数据：」「结论：」「建议：」，少用「怎么做」 |
| 口语 | P0 禁用：挺好的、超级、搞定、很明显（无数时） |

## 句式示例（通用）

```text
对比：低分段不良率为 8.2%，高分段为 0.3%。
建议：宜同时参考分数与额度规则，不宜仅凭分数一项确定额度。
收束：总结：按数据核对、规则、模型顺序推进。
```

## 交付件书面体（策略说明 / 操作指引 / 方案说明）

适用：向外部协作方确认字段、写策略摘录、写需求说明、写方案章节。  
参照常见手工整理交付件写法：先写用途与优先级，再写条件与公式，再写须确认事项。

| 维度 | 宜 | 不宜 |
|------|----|------|
| 开篇 | 「…依据说明」；「主要用于…」；「优先级顺序为：A-B-C」 | 「致各位同事」「我们希望能够」「恳请」等客套堆砌 |
| 规则摘录 | 「1.条件 2.计算 3.结果」；公式直写「月收入=…」 | 把公式改写成散文抒情；「我们据此认为系统一定有…」 |
| 操作核对 | 「核对…是否…」；「…可帮助判断…」；「查看…」 | 「请务必深刻理解」「需要注意的是」说教开场 |
| 材料边界 | 「有依据：…交付件写明…」；「现有交付件中未见明确表述，请确认是否具备」 | 「有据证明」「银数一定持有」「证据确凿」 |
| 材料性质 | 标明「手工整理交付件中的表述」；生产落库/导出「以对方确认为准」 | 把整理稿直接写成正式数据字典或接口承诺 |
| 限定 | 「说明：…」；「不宜在未…前作定论」 | 「显而易见」「毫无疑问」 |
| 收束 | 「优先确认 / 其次确认」；「经确认后，据此更新…」 | 「期待您的回复」「谢谢配合」占半页 |

分析报告页结论仍可用「数据 / 结论 / 建议」；策略与需求类正文优先用上表交付件体，二者可按文档类型选用，勿混成聊天邮件腔。
